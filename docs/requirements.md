# 要件

開発者が PO 役のエージェントと目標を決め、エージェントのチームが MVP と最終 PR まで自走する開発環境の要件。配置の判断は ADR（`adr/pi-durable-dev-env/`）に、構成の全体像は [architecture.md](architecture.md) に、進め方は [roadmap.md](roadmap.md) に置く。

## 利用者と利用の流れ

利用者は開発者 1 人。チームでの共有は考えない。

作業させるのは、GitHub にある作業リポジトリ（リポジトリは作成済みとする）。このリポジトリとは別の git リポジトリで、目標ごとにコンテナの中へクローンする。

1. 開発者が Slack で PO にメンションしてスレッドを始め、作業リポジトリと目標を書く
2. 開発者は PO とスレッドで対話し、目標を決める。目標の大きさは 1 つの機能、1 つのアプリ、1 つの要望など
3. 目標が決まったら、チームが完了まで自走する。開発者が離席していても、マシンを閉じていても作業は進む
4. 確認や判断が必要になったら、PO がスレッドで開発者にメンションする
5. 開発者は MVP やモックをプレビュー URL で動かして確認し、スレッドで PO にフィードバックする
6. 最後に、開発者は目標の成果物をまとめた最終 PR を 1 本レビューする。それ以外の中間成果物はほとんど見ない

目標を複数並べて、同時に進めることがある。1 つの目標が、1 つの Slack スレッド、1 つのセッション、1 つの PO、1 つのコンテナに対応する。チームは目標を増やさない。サブエージェントは同じコンテナの中で作業する。

## チームの役割と承認

| 役割 | 成果物 |
|---|---|
| PO | 目標、承認の依頼、開発者への報告 |
| spec | 仕様の文書 |
| design | 設計 |
| impl | コード |
| test | テストコード。impl から独立して、仕様をもとに書く |
| review | レビューの記録 |

各役割の視点や手順（何を基準に仕様を決めるか、どう実装しテストを書くか）と、それを支えるハーネスは、あとから整備する。

承認:

- 途中の承認は、MVP やモックを動かして行う
- 最後の承認は、最終 PR のレビューで行う
- PR は手段で、粒度は決めない。チーム内では、review と impl の連携のために細かい PR を作ってよい。チーム内の PR はコンテナの中のブランチにして、目標ブランチに向けてマージする。開発者が GitHub で見る PR を最終 PR の 1 本にするため

MVP とモックは、コンテナの中で動かしてプレビュー URL で公開し、開発者のブラウザで確認する。

## コンテキストの要件

1 つのセッションでエージェントを動かし続けると、不要なコンテキストがたまっていく。これを避ける。

- エージェントは、作業の単位ごとに新しいコンテキストで起動する
- 必要な情報は、エージェントが必要なときにツールでコンテキスト DB から取りに行く
- チャットログは記録として残す。エージェント自身のコンテキストには載せ続けない

履歴を残す目的:

- 中断した作業の再開
- 過去の判断の振り返り
- プロジェクト知識の蓄積（目標をまたいで次の目標で使う）

DB は 2 種類に分ける。durable のストレージは 1 つの持ち主（DO）しか開けないので、並行する目標で共有する知識は別の DO に置く。

| DB | 中身 | 単位 | 置き場所 |
|---|---|---|---|
| セッション DB | durable の会話ログと再開の状態 | 目標ごとに 1 つ | セッション DO の SQLite |
| コンテキスト DB | 知識、判断、タスクの状態、目標の記録。行ごとに `goal_id` を持つ | 作業リポジトリごとに 1 つ | リポジトリ DO の SQLite。複数のセッション DO から RPC で読み書きする |

目標を終えても、コンテキスト DB のデータは残る。目標の記録は、行を終了扱いにするだけにする。

git に残すのは仕様の文書だけ。知識や判断はコンテキスト DB に残し、必要以上に git に入れない。

## データと隔離の要件

置き場所（[ADR 0002](../adr/pi-durable-dev-env/0002-run-on-cloudflare.md)）:

| もの | 場所 |
|---|---|
| 本体（Worker のコード）、指示とガードの設定（`agents/<repo>/`） | このリポジトリ。Worker と一緒にデプロイする |
| Workers AI を呼ぶ Cloudflare の API トークン、GitHub App の秘密鍵、Slack の署名シークレットと bot トークン | Worker の secret |
| セッション DB とコンテキスト DB | DO の SQLite。`<repo>` は GitHub の remote URL で識別する |
| 作業リポジトリのクローンと目標ブランチ | コンテナの `/workspace` |
| `/workspace` の退避 | コンテナの snapshot |

隔離で守るのは、本体と資格情報にエージェントが届かないこと。外部に情報が出る経路は防がない。GitHub とコンテナの中での操作は縛らない。

縛るもの:

- 本体、設定、DB、資格情報はコンテナに入れない。コンテナは Worker だけが起動する
- GitHub の資格情報はコンテナに渡さず、Egress Worker が GitHub への要求に差し込む。差し込むのは GitHub App のインストールトークンで、作業リポジトリと `contents` / `pull_requests` の書き込みだけに絞る。ほかのリポジトリや gist に書けると、GitHub の中でも外に出す経路になるため。長期のトークン（PAT）は使わない
- Cloudflare の API トークンと Slack のトークンはコンテナに渡さない
- エージェントがコンテキスト DB を読み書きするのは、ホスト側のツール（DO の RPC）を通したときだけにする。どの目標の行を見せるかはリポジトリ DO が決める
- Slack からの要求は署名を検証し、許可したユーザー ID からのものだけを受け付ける
- 検証用の Webhook は Bearer トークンで認証する
- プレビュー URL は認証を通らないと届かないようにする（方式は M7 で決める）

縛らないもの:

- コンテナの中のコマンドの実行とファイルの編集
- コンテナの中の `.git` の読み書き（commit、branch、merge、config、hooks）
- コンテナからの外向きの接続。パッケージのレジストリなどに制限なく届く
- 作業リポジトリへの GitHub の読み書き（fetch、push、issue や PR の操作）。最終 PR はエージェントが作ってよい

外部に送るデータ: 作業リポジトリのコードと会話は、Workers AI（Cloudflare）と Slack に送ってよい。DeepSeek 社の API には送らない。

commit の作者は環境変数（`GIT_AUTHOR_NAME` など）で渡す。PR は GitHub の REST API で作る（差し込み方式では `gh` の GraphQL が認証されないため）。

## 動かす場所とコスト

- Cloudflare で常時稼働する（Worker、DO、Containers）。開発は `wrangler dev`（Miniflare と手元の Docker）で行う
- モデルは DeepSeek V4.1 Flash を Workers AI（`@cf/deepseek-ai/deepseek-v4.1-flash-1017`）で呼ぶ
- Slack は Free プランで始める。90 日より前のスレッドを読み返す必要が出たら Pro にする
- 費用の見積もり（2026-11 時点、月に目標 20 件、コンテナは 1 vCPU・4 GiB・16 GB で月 120 時間起動する場合）: Cloudflare が約 $11〜19（Workers Paid の $5 を含む）、Workers AI（DeepSeek V4.1 Flash。入力 $0.30、出力 $1.20、キャッシュ $0.006 / 1M トークン）が約 $38、合計で約 $50〜60。Slack Pro にすると 1 ユーザーあたり月 $7.25〜8.75 が加わる
- 費用はトークン量で大きく変わる。上限は M8 で usage を見て決める

## やらないこと

- チームでの共有。サンプル由来の、複数人で同じセッションに入る機能は使わない
- `wrangler dev` 以外の形でローカルで動かすこと
- チーム内の PR を GitHub に作ること、チーム内のブランチを GitHub に push すること（必要になったら見直す）
- このリポジトリを作業リポジトリにすること。このリポジトリ自体を開発させるときは、別のリポジトリを新しく作って作業させ、成果をこのリポジトリに回収する
- 各役割の視点や手順の詳細（あとから整備する）
