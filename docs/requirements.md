# 要件

開発者が PO 役のエージェントと目標を決め、エージェントのチームが MVP と最終 PR まで自走する開発環境の要件。配置の判断は ADR（`adr/pi-durable-dev-env/`）に、構成の全体像は [architecture.md](architecture.md) に、進め方は [roadmap.md](roadmap.md) に置く。

## 利用者と利用の流れ

利用者は開発者 1 人。チームでの共有は考えない。

作業させるのは、GitHub からこのリポジトリの `workspace/` にクローンした作業リポジトリ（リポジトリは作成済みとする）。作業リポジトリは別の git リポジトリで、このリポジトリの git には入れない。

1. 開発者が Orca で作業リポジトリに worktree を作り、その worktree で `just po` を実行して PO を起動する
2. 開発者は PO とターミナルで対話し、目標を決める。目標の大きさは 1 つの機能、1 つのアプリ、1 つの要望など
3. 目標が決まったら、チームが完了まで自走する。開発者が離席していても作業は進む
4. 確認や判断が必要になったら、PO が開発者に通知する
5. 開発者は MVP やモックを動かして確認し、PO にフィードバックする
6. 最後に、開発者は目標の成果物をまとめた最終 PR を 1 本レビューする。それ以外の中間成果物はほとんど見ない

worktree を複数並べて、目標を同時に進めることがある。1 つの worktree が、1 つの目標、1 つの PO、1 つのセッションに対応する。チームは worktree を増やさない。サブエージェントは同じ worktree の中で作業する。

## チームの役割と承認

| 役割 | 成果物 |
|---|---|
| PO | 目標、承認の依頼、開発者への報告 |
| spec | 仕様の文書 |
| design | 設計 |
| impl | コード |
| test | テストコード。impl から独立して、仕様をもとに書く |
| review | レビューの記録 |

各役割の視点や手順（何を基準に仕様を決めるか、どう実装しテストを書くか）と、それを支えるハーネスは、あとから整備する。

承認:

- 途中の承認は、MVP やモックを動かして行う
- 最後の承認は、最終 PR のレビューで行う
- PR は手段で、粒度は決めない。チーム内では、review と impl の連携のために細かい PR を作ってよい。チーム内の PR はローカルのブランチにして、worktree のブランチ（目標ブランチ）に向けてマージする。開発者が GitHub で見る PR を最終 PR の 1 本にするため

MVP とモックは、コンテナで動かしてポートフォワードし、ホストのブラウザで確認する。

## コンテキストの要件

1 つのセッションでエージェントを動かし続けると、不要なコンテキストがたまっていく。これを避ける。

- エージェントは、作業の単位ごとに新しいコンテキストで起動する
- 必要な情報は、エージェントが必要なときにツールでコンテキスト DB から取りに行く
- チャットログは記録として残す。エージェント自身のコンテキストには載せ続けない

履歴を残す目的:

- 中断した作業の再開
- 過去の判断の振り返り
- プロジェクト知識の蓄積（worktree をまたいで次の目標で使う）

DB は 2 種類に分ける。durable のストレージは 1 プロセスでしか開けないので、並行する worktree で共有できない。

| DB | 中身 | 単位 | 開き方 |
|---|---|---|---|
| セッション DB | durable の会話ログと再開の状態 | worktree ごとに 1 ファイル | そのプロセスだけが開く |
| コンテキスト DB | 知識、判断、タスクの状態、worktree の記録。行ごとに `worktree_id` を持つ | 作業リポジトリごとに 1 ファイル | 複数のプロセスが WAL で同時に開く |

worktree を消しても、コンテキスト DB のデータは残る。worktree の記録は、行を終了扱いにするだけにする。

git に残すのは仕様の文書だけ。知識や判断はコンテキスト DB に残し、必要以上に git に入れない。

## データと隔離の要件

置き場所: 検証のため、すべてをこのリポジトリの下にまとめる（[ADR 0001](../adr/pi-durable-dev-env/0001-separate-agent-env-from-work-repos.md)）。

| もの | 場所 | git |
|---|---|---|
| 本体（`host/`、npm の依存、`justfile`） | このリポジトリ | コミットする |
| 指示とガードの設定 | `agents/<repo>/` | コミットする |
| 資格情報 | `.data/` | 無視する |
| セッション DB とコンテキスト DB | `.data/repos/<repo>/`。`<repo>` は GitHub の remote URL で識別する | 無視する |
| 作業リポジトリと worktree | `workspace/` | 無視する |

隔離で守るのは、開発に関係のない外部に情報が出ないことと、ホストで任意のコードが動かないこと。GitHub と開発環境の中での操作は縛らない。

縛るもの:

- コンテナから接続できる先は、GitHub とパッケージのレジストリなど、開発環境に関係するものだけにする
- コンテナにマウントするのは、`workspace/` の下の worktree と共通の `.git` だけにする。本体、設定、DB、資格情報はマウントしない。コンテナは host だけが起動する
- `.git/hooks` と `.git/config` はコンテナから読み取り専用にする。ここに仕込まれたものは、開発者や Orca がホストで git を実行したとき（`git status` でも `core.fsmonitor` が動く）にホストで動き、接続先の制限も資格情報の隔離も素通りするため
- GitHub のトークンは、作業リポジトリだけに権限を絞る。ほかのリポジトリや gist に書けると、GitHub の中でも外に出す経路になるため
- ChatGPT の資格情報はコンテナに渡さない
- エージェントがコンテキスト DB を読み書きするのは、ホスト側のツールを通したときだけにする。どの worktree の行を見せるかはホストが決める

縛らないもの:

- コンテナの中のコマンドの実行とファイルの編集
- `.git` のうち hooks と config 以外の読み書き（commit、branch、merge など）
- 作業リポジトリへの GitHub の読み書き（fetch、push、issue や PR の操作）。最終 PR はエージェントが作ってよい

`.git/config` を読み取り専用にするので、エージェントは `git config` を変えられない。commit の作者は環境変数（`GIT_AUTHOR_NAME` など）で渡す。husky などで hooks を使う作業リポジトリは、開発者がホストで先に設定しておく。

## 動かす場所とコスト

- 当面はローカルで動かす。常時稼働（M11 の Cloudflare）は将来の選択肢として残す
- ChatGPT Plus の定額枠に収める

## やらないこと

- チームでの共有
- 当面の常時稼働
- チーム内の PR を GitHub に作ること（必要になったら見直す）
- このリポジトリを作業リポジトリにすること。このリポジトリ自体を開発させるときは、別のリポジトリを新しく作って `workspace/` で作業させ、成果をこのリポジトリに回収する
- 各役割の視点や手順の詳細（あとから整備する）
